# 정보보안기사 오답노트 - 이메일 / 웹 보안 / SQL Injection / DNSSEC / FTP

## 1. 이메일 시스템에서 호스트로부터 전달된 메일을 사용자의 메일함으로 저장하는 역할은?

**정답: ④ MDA**

### 1) 문제 이해하기

이메일 시스템에는 메일을 보내고, 전달하고, 받는 여러 가지 역할이 있어.

여기서 중요한 건 각각의 역할을 구분하는 거야.

우리가 이메일을 보낸다고 생각해 보자.

1. 사용자가 이메일 프로그램에서 메일을 작성한다.
2. 작성한 메일을 메일 서버로 전송한다.
3. 메일 서버가 상대방의 메일 서버로 메일을 전달한다.
4. 상대방의 메일 서버가 받은 메일을 사용자의 메일함에 저장한다.
5. 사용자가 이메일 프로그램으로 메일을 확인한다.

이 과정에서 각각의 역할을 담당하는 것이 SMTP, MTA, MUA, MDA야.

### 2) 각 용어 이해하기

**① SMTP (Simple Mail Transfer Protocol)**

- 이메일을 전송하기 위한 통신 프로토콜이야.
- 쉽게 말하면 이메일을 보내기 위해 사용하는 전송 규칙이야.
- 메일을 발신하거나 메일 서버 간에 전달할 때 사용해.

예를 들어 내가 친구에게 이메일을 보낸다면 SMTP를 통해 메일이 전송되는 거야.

**② MTA (Mail Transfer Agent)**

- 메일을 다른 메일 서버로 전달하는 역할을 해.
- 쉽게 말하면 메일을 목적지까지 운반하는 택배 기사라고 생각하면 돼.

예를 들어 A 메일 서버가 받은 메일을 B 메일 서버로 전달하는 역할이야.

**③ MUA (Mail User Agent)**

- 사용자가 이메일을 작성하거나 확인할 때 사용하는 프로그램이야.
- 쉽게 말하면 사용자가 직접 사용하는 이메일 프로그램이야.

대표적인 예시:
- Outlook
- Thunderbird
- 스마트폰 이메일 앱

**④ MDA (Mail Delivery Agent)**

- 전달받은 메일을 사용자의 메일함에 저장하는 역할을 해.
- 쉽게 말하면 택배를 최종 목적지인 집 앞에 전달하는 역할이야.

메일 서버가 받은 메일을 실제 사용자의 메일함에 넣어 주는 거지.

### 3) 정답이 ④번인 이유

문제에서 가장 중요한 표현은 다음과 같아.

"사용자의 메일함으로 저장하는 역할"

메일을 다른 서버로 전달하는 게 아니라, 최종적으로 사용자의 메일함에 저장하는 역할이므로 MDA가 정답이야.

### 4) 다른 보기가 틀린 이유

- ① SMTP: 이메일을 전송하기 위한 통신 프로토콜이야.
- ② MTA: 메일을 다른 메일 서버로 전달하는 역할이야.
- ③ MUA: 사용자가 이메일을 작성하고 확인하는 프로그램이야.
- ④ MDA: 전달받은 메일을 사용자의 메일함에 저장하는 역할이야.

### 5) 시험 암기

| 구분 | 역할 |
|---|---|
| SMTP | 메일 전송 프로토콜 |
| MTA | 메일 서버 간 전달 |
| MUA | 사용자가 사용하는 메일 프로그램 |
| MDA | 메일을 사용자의 메일함에 저장 |

**핵심 암기:**
- SMTP = 전송 규칙
- MTA = 서버 간 전달
- MUA = 사용자 프로그램
- MDA = 메일함 저장

## 2. 다음 내용과 같은 보안대책을 적용할 수 있는 설계 항목은?

**정답: ④ 예외처리**

### 1) 문제 이해하기

문제에서 제시한 코드는 다음과 같아.

```xml
<error-page>
    <error-code>500</error-code>
    <location>/WEB-INF/jsp/common/error/500error.jsp</location>
</error-page>
```

이 코드는 웹 애플리케이션에서 특정 오류가 발생했을 때 어떤 페이지를 보여줄 것인지 설정하는 코드야.

여기서 중요한 건 HTTP 상태 코드인 500이야.

### 2) HTTP 500 오류란?

HTTP 500은 Internal Server Error의 약자로, 서버 내부에서 오류가 발생했다는 의미야.

쉽게 말하면 사용자가 웹사이트에 접속했는데 서버 내부에서 문제가 발생해서 정상적으로 처리하지 못한 상황이야.

예를 들어 다음과 같은 상황이 있을 수 있어.

- 서버 내부 프로그램에 오류가 발생한 경우
- 데이터 처리 과정에서 예외가 발생한 경우
- 서버에서 예상하지 못한 문제가 발생한 경우

이때 사용자에게 서버 내부의 상세한 오류 정보를 그대로 보여주면 보안상 문제가 생길 수 있어.

예를 들어 다음과 같은 정보가 노출될 수 있거든.

- 서버의 실제 경로
- 프로그램 내부 구조
- 데이터베이스 관련 정보
- 소스코드 일부
- 시스템 내부 설정 정보

공격자가 이런 정보를 얻으면 추가적인 공격에 활용할 수 있어.

### 3) 제시된 코드의 역할

```xml
<error-page>
    <error-code>500</error-code>
    <location>/WEB-INF/jsp/common/error/500error.jsp</location>
</error-page>
```

이 코드는 HTTP 500 오류가 발생했을 때 지정된 오류 페이지인 `500error.jsp`를 보여주도록 설정하는 거야.

즉, 서버 내부의 상세한 오류 내용을 사용자에게 그대로 노출하지 않고 별도의 오류 페이지를 보여주는 방식이지.

이런 처리를 통해 오류 정보 노출을 줄일 수 있어.

### 4) 정답이 ④번인 이유

오류가 발생했을 때 적절한 오류 페이지를 보여주도록 처리하는 것은 예외처리에 해당해.

예외처리란 프로그램 실행 중 예상하지 못한 오류가 발생했을 때 프로그램이 비정상적으로 종료되거나 민감한 정보가 노출되지 않도록 처리하는 것을 말해.

따라서 정답은 ④ 예외처리야.

### 5) 다른 보기가 틀린 이유

**① 중요자원 접근 통제**

- 중요한 파일이나 데이터에 접근할 수 있는 권한을 제한하는 거야.
- 예를 들어 관리자만 특정 설정 파일에 접근할 수 있도록 하는 방식이지.
- 오류 페이지를 설정하는 내용과는 관계가 없어.

**② 세션통제**

- 사용자의 로그인 상태나 세션을 안전하게 관리하는 거야.
- 세션 만료, 세션 ID 관리, 세션 탈취 방지 등이 해당해.
- 오류 페이지 설정과는 관계가 없어.

**③ DBMS 조회 및 결과 검증**

- 데이터베이스에 전달하는 조회문과 조회 결과가 적절한지 확인하는 거야.
- SQL Injection 방지나 데이터 검증 등이 관련돼.
- 오류 페이지 설정과는 관계가 없어.

**④ 예외처리**

- 프로그램에서 오류가 발생했을 때 적절하게 처리하는 거야.
- 오류 페이지 설정, 예외 상황 처리, 오류 정보 노출 방지 등이 해당해.

### 6) 시험 암기

- HTTP 500 = 서버 내부 오류
- 오류 발생 시 별도의 오류 페이지 표시 = 예외처리
- 상세한 오류 정보 노출 방지 = 예외처리와 관련

**핵심 암기:**
오류가 발생했을 때 어떻게 처리할 것인가? → 예외처리

## 3. 다음 내용은 취약한 JAVA 코드 일부이다. 이에 대한 설명으로 옳은 것은?

**정답: ③ 의도하지 않은 운영체제 명령어가 실행되지 않도록 입력값 검증을 수행한다.**

### 1) 문제에 나온 코드 이해하기

```java
String date = request.getParameter("date");
String command = new String("cmd.exe /c backuplog.bat");
Runtime.getRuntime().exec(command + date);
```

처음 보면 복잡해 보이지만 하나씩 보면 어렵지 않아.

**첫 번째 줄**

```java
String date = request.getParameter("date");
```

- 사용자가 웹사이트에 입력한 `date` 값을 가져오는 코드야.
- 즉, 외부에서 전달된 입력값을 가져오는 거지.

예를 들어 사용자가 다음과 같은 값을 입력했다고 생각해 보자.

```text
2026-11-05
```

그러면 date 변수에 `2026-11-05`가 저장돼.

**두 번째 줄**

```java
String command = new String("cmd.exe /c backuplog.bat");
```

- Windows 명령 프롬프트를 실행하기 위한 명령어를 저장하는 코드야.
- `backuplog.bat`이라는 배치 파일을 실행하도록 되어 있어.

여기서 `.bat` 파일은 Windows에서 명령어들을 실행할 수 있는 배치 파일이야.

**세 번째 줄**

```java
Runtime.getRuntime().exec(command + date);
```

이 부분이 가장 중요해.

- `Runtime.getRuntime().exec()`는 운영체제 명령어를 실행하는 기능이야.
- 앞에서 만든 command에 사용자가 입력한 date 값을 붙여서 실행하고 있어.

즉, 사용자가 입력한 값이 운영체제 명령어에 그대로 들어가는 구조야.

### 2) 어떤 보안 취약점이 발생할 수 있을까?

이런 코드는 운영체제 명령어 삽입(Command Injection) 취약점이 발생할 수 있어.

쉽게 말하면 원래 프로그램이 실행하려던 명령어에 공격자가 악의적인 명령어를 추가해서 실행시키는 공격이야.

예를 들어 정상적인 입력값은 다음과 같겠지.

```text
2026-11-05
```

그런데 공격자가 정상적인 날짜 대신 명령어로 해석될 수 있는 값을 입력하면 문제가 생길 수 있어.

Windows에서는 명령어 연결에 `&` 같은 문자를 사용할 수 있어.

예를 들어 다음과 같은 입력을 생각해 보자.

```text
2026-11-05 & whoami
```

입력값을 제대로 검증하지 않고 명령어에 붙여 실행한다면 원래 의도한 백업 작업 외에 다른 운영체제 명령어까지 실행될 가능성이 생겨.

이것이 바로 Command Injection이야.

※ 실제 공격 성공 여부는 명령어 실행 방식, 입력값 처리, 운영체제 환경 등에 따라 달라질 수 있어.

### 3) 정답이 ③번인 이유

문제의 핵심은 사용자가 입력한 값이 운영체제 명령어에 그대로 포함된다는 점이야.

따라서 공격자가 악의적인 명령어를 입력하지 못하도록 입력값을 검증해야 해.

예를 들어 날짜를 입력받는 기능이라면 날짜 형식만 허용하도록 제한할 수 있어.

```text
허용되는 입력:
2026-11-05

허용하지 않는 입력:
2026-11-05 & whoami
```

이런 식으로 프로그램이 원래 의도한 형식의 값만 받도록 해야 해.

가능하면 외부 입력값을 명령어에 직접 연결하지 않고, 운영체제 명령어 실행 자체를 피하거나 안전한 API를 사용하는 것이 더 좋아.

따라서 정답은 ③번이야.

### 4) 다른 보기가 틀린 이유

**① 문자열을 사용할 때 포맷 문자열이 적절히 사용되었는지 검사한다.**

- 포맷 문자열 취약점(Format String Vulnerability)에 대한 대응이야.
- 문자열 출력이나 서식 지정 과정에서 발생하는 취약점을 방지하기 위한 내용이지.
- 이번 문제는 문자열 포맷이 아니라 운영체제 명령어 실행에 사용자의 입력값이 들어가는 것이 문제야.

**② 배열을 사용할 때에는 배열의 크기를 확인하고 크기를 넘어가는 접근이 일어나지 않도록 한다.**

- 배열의 범위를 벗어나는 접근을 방지하기 위한 내용이야.
- 배열 인덱스가 실제 크기를 초과하면 메모리 관련 문제가 발생할 수 있어.
- 이번 문제의 핵심인 명령어 삽입과는 관계가 없어.

**③ 의도하지 않은 운영체제 명령어가 실행되지 않도록 입력값 검증을 수행한다.**

- 사용자의 입력값이 운영체제 명령어에 포함되는 상황이야.
- 악의적인 명령어가 실행되지 않도록 입력값을 검증해야 해.
- 정답이야.

**④ 허용된 형식의 파일만 업로드할 수 있도록 확장자를 검사한다.**

- 파일 업로드 취약점에 대한 대응이야.
- 예를 들어 `.jpg`, `.png` 등 허용된 확장자만 업로드하도록 제한하는 방식이지.
- 이번 문제는 파일 업로드가 아니라 운영체제 명령어 실행과 관련된 문제야.

### 5) 시험 암기

- Runtime.getRuntime().exec() = 운영체제 명령어 실행
- 사용자 입력값을 명령어에 그대로 연결 = Command Injection 위험
- Command Injection 대응 = 입력값 검증, 명령어 실행 최소화, 안전한 API 사용

**핵심 암기:**
사용자 입력값이 운영체제 명령어에 들어간다 → Command Injection

## 4. 다음 내용에서 설명하고 있는 SQL Injection 공격 유형은?

**정답: ① Blind based SQL Injection**

### 1) 문제 이해하기

문제에서 중요한 표현은 다음과 같아.

"데이터베이스에 참 또는 거짓 질의를 하고 애플리케이션 응답에 따라 데이터베이스의 내용을 추측하여 공격하는 방식"

이 문장에서 핵심은 참(True) 또는 거짓(False)이야.

이런 방식의 공격을 Blind SQL Injection이라고 해.

### 2) SQL Injection이란?

SQL Injection은 웹사이트가 데이터베이스에 전달하는 SQL 문에 공격자가 악의적인 내용을 삽입하는 공격이야.

쉽게 말하면 웹사이트가 데이터베이스에 전달하는 질문을 공격자가 조작하는 거야.

예를 들어 로그인 기능이 있다고 생각해 보자.

사용자가 아이디와 비밀번호를 입력하면 웹사이트는 데이터베이스에 해당 계정이 있는지 확인하는 SQL문을 실행해.

그런데 공격자가 입력값에 악의적인 SQL 구문을 넣으면 원래 의도하지 않은 데이터베이스 조회나 조작이 발생할 수 있어.

### 3) Blind SQL Injection 이해하기

Blind SQL Injection은 데이터베이스의 내용을 직접 보여주지 않는 상황에서도 공격자가 참과 거짓에 따른 애플리케이션의 반응을 관찰하면서 정보를 알아내는 공격이야.

예를 들어 공격자가 데이터베이스에 다음과 같은 질문을 던진다고 생각해 보자.

```text
질문 1: 첫 번째 글자가 A인가?
질문 2: 첫 번째 글자가 B인가?
질문 3: 첫 번째 글자가 C인가?
```

웹사이트의 반응이 다음과 같다고 해보자.

| 질문 | 웹사이트 반응 |
|---|---|
| 첫 번째 글자가 A인가? | 정상적인 페이지 |
| 첫 번째 글자가 B인가? | 오류 페이지 |
| 첫 번째 글자가 C인가? | 오류 페이지 |

공격자는 정상적인 페이지가 나온 질문을 통해 첫 번째 글자가 A라는 사실을 추측할 수 있어.

이런 식으로 참과 거짓에 따른 반응을 반복해서 확인하면 데이터베이스의 정보를 알아낼 수 있는 거야.

이름에 Blind(눈이 보이지 않는)가 들어가는 이유도 여기 있어.

데이터베이스의 실제 결과를 직접 볼 수 없기 때문에 애플리케이션의 반응을 통해 간접적으로 정보를 알아내는 거지.

### 4) 정답이 ①번인 이유

문제에서 다음과 같은 표현이 나왔어.

- 참 또는 거짓 질의
- 애플리케이션 응답에 따라
- 데이터베이스의 내용을 추측

이 세 가지가 Blind SQL Injection의 대표적인 특징이야.

따라서 정답은 ①번이야.

### 5) 다른 보기가 틀린 이유

**② Stored Procedure based SQL Injection**

- 저장 프로시저(Stored Procedure)를 이용하는 SQL Injection 유형이야.
- 저장 프로시저는 데이터베이스에 미리 저장해 놓은 SQL 명령어 묶음이라고 생각하면 돼.
- 저장 프로시저를 안전하지 않게 호출하거나 입력값을 처리하면 SQL Injection이 발생할 수 있어.
- 참과 거짓에 따른 응답을 관찰하는 공격을 의미하지는 않아.

**③ Error based SQL Injection**

- 데이터베이스에서 발생하는 오류 메시지를 이용하는 공격이야.
- 오류 메시지에 데이터베이스 구조나 정보가 포함될 수 있다는 점을 이용하지.
- 즉, 오류 메시지를 통해 정보를 알아내는 방식이야.

**④ Union based SQL Injection**

- SQL의 UNION 연산자를 이용하는 공격이야.
- 기존 조회 결과에 다른 SELECT문의 결과를 결합하여 데이터베이스 정보를 가져오는 방식이야.
- 데이터베이스의 조회 결과를 직접 확인할 수 있는 상황에서 사용될 수 있어.

### 6) 시험 암기

| 공격 유형 | 핵심 특징 |
|---|---|
| Blind SQL Injection | 참/거짓 반응으로 정보 추측 |
| Stored Procedure | 저장 프로시저 악용 |
| Error based | 오류 메시지로 정보 획득 |
| Union based | UNION으로 조회 결과 결합 |

**핵심 암기:**
- 참/거짓으로 추측한다 → Blind
- 오류 메시지를 이용한다 → Error based
- UNION을 이용한다 → Union based
- 저장 프로시저를 이용한다 → Stored Procedure based

## 5. DNS 데이터 위변조 공격을 방지하기 위한 표준기술인 DNSSEC의 리소스 레코드에 대한 설명으로 옳지 않은 것은?

**정답: ① NSEC(Next Secure): DNS 데이터 존재의 인증을 위해 정의된 리소스 레코드**

### 1) DNSSEC란?

먼저 DNS부터 이해해 보자.

DNS(Domain Name System)는 도메인 이름을 IP 주소로 변환해 주는 시스템이야.

예를 들어 사용자가 웹 브라우저에 다음과 같이 입력한다고 생각해 보자.

```text
www.example.com
```

컴퓨터는 해당 도메인에 대응하는 IP 주소를 알아내야 실제 서버에 접속할 수 있어.

이때 DNS가 도메인 이름에 해당하는 IP 주소를 찾아주는 역할을 해.

그런데 DNS 응답이 공격자에 의해 위조된다면 어떻게 될까?

예를 들어 정상적인 사이트에 접속하려고 했는데 공격자가 위조한 IP 주소를 전달하면 사용자가 가짜 사이트로 접속하게 될 수 있어.

이런 문제를 방지하기 위해 사용하는 기술이 DNSSEC야.

### 2) DNSSEC란?

DNSSEC(Domain Name System Security Extensions)는 DNS 데이터의 위변조를 방지하고 데이터의 출처와 무결성을 검증하기 위한 보안 확장 기술이야.

쉽게 말하면 DNS 응답에 전자서명을 붙여서 해당 데이터가 정상적인 데이터인지 확인할 수 있도록 하는 기술이지.

여기서 중요한 건 DNSSEC의 주요 리소스 레코드들이야.

### 3) 각 리소스 레코드 이해하기

**① NSEC (Next Secure)**

- DNS 영역(zone)에서 특정 이름 다음에 존재하는 이름을 알려주는 리소스 레코드야.
- DNS에 특정 도메인 이름이나 레코드가 존재하지 않는다는 사실을 인증하는 데 사용돼.
- 즉, 존재하지 않는 DNS 데이터에 대한 인증된 부재 증명을 제공하는 역할이야.

여기서 문제의 설명이 잘못됐어.

문제에서는 "DNS 데이터 존재의 인증"이라고 설명했는데, NSEC의 핵심은 DNS 데이터가 존재한다는 것을 인증하는 것이 아니라 존재하지 않는다는 것을 증명하는 거야.

따라서 ①번이 정답이야.

**② RRSIG (Resource Record Signature)**

- DNS의 리소스 레코드 집합(RRset)에 대한 전자서명 정보를 저장하는 리소스 레코드야.
- DNS 데이터가 위조되거나 변조되지 않았는지 검증하는 데 사용돼.
- 쉽게 말하면 DNS 데이터에 붙이는 전자서명이라고 생각하면 돼.

**③ DNSKEY (DNS Key)**

- DNS 영역(zone)의 공개키 정보를 저장하는 리소스 레코드야.
- DNSSEC에서 전자서명을 검증할 때 필요한 공개키를 제공해.
- 쉽게 말하면 전자서명이 진짜인지 확인할 때 사용하는 공개키를 제공하는 역할이야.

**④ DS (Delegation Signer)**

- 하위 도메인의 DNSKEY 정보를 상위 영역에서 인증할 수 있도록 연결하는 리소스 레코드야.
- 일반적으로 하위 영역의 DNSKEY에 대한 해시 정보를 저장해.
- DNSSEC의 신뢰 체인을 구성하는 데 사용돼.

쉽게 말하면 상위 도메인이 하위 도메인의 공개키를 신뢰할 수 있도록 연결해 주는 역할이야.

### 4) 정답이 ①번인 이유

NSEC는 DNS 데이터가 존재한다는 사실을 인증하는 것이 아니라, DNS 데이터가 존재하지 않는다는 사실을 인증하는 데 사용돼.

문제의 설명은 이 부분이 잘못됐기 때문에 ①번이 정답이야.

### 5) 다른 보기가 맞는 이유

- ① NSEC: 존재하지 않는 DNS 데이터에 대한 인증된 부재 증명. 문제의 설명이 잘못됐어.
- ② RRSIG: DNS 리소스 레코드 집합에 대한 전자서명 정보를 저장해.
- ③ DNSKEY: DNS 영역의 공개키 정보를 저장해.
- ④ DS: 상위 영역과 하위 영역의 DNSSEC 신뢰 관계를 연결하는 데 사용돼.

### 6) 시험 암기

| 레코드 | 역할 |
|---|---|
| NSEC | DNS 데이터가 존재하지 않는다는 사실을 증명 |
| RRSIG | DNS 데이터의 전자서명 |
| DNSKEY | 공개키 저장 |
| DS | 상위 영역과 하위 영역의 신뢰 관계 연결 |

**핵심 암기:**
- NSEC = 존재하지 않음 증명
- RRSIG = 전자서명
- DNSKEY = 공개키
- DS = 위임 및 신뢰 연결

※ 참고로 DNSSEC에는 NSEC3도 있어. NSEC3 역시 인증된 부재 증명을 제공하지만, 이름을 해시하는 방식으로 NSEC의 일부 정보 노출 문제를 개선한 기술이야.

## 6. 웹 취약점 중 파일 업로드 취약점에 대한 시큐어 코딩 시 대응 방안으로 옳지 않은 것은?

**정답: ④ 파일명에 경로조작이 가능한 '..', '/', '\' 문자는 제거하고 사용할 수 있도록 필터링한다.**

### 1) 파일 업로드 취약점이란?

파일 업로드 취약점은 웹사이트에서 파일을 업로드할 때 적절한 검증이나 제한이 이루어지지 않아 발생하는 보안 취약점이야.

예를 들어 게시판에 이미지 파일을 업로드하는 기능이 있다고 생각해 보자.

정상적인 사용자는 다음과 같은 파일을 업로드하겠지.

```text
profile.jpg
```

그런데 공격자가 웹 서버에서 실행될 수 있는 악성 파일을 업로드할 수 있다면 문제가 생겨.

예를 들어 서버에서 실행 가능한 스크립트 파일이 업로드되고 실행된다면 서버가 공격당할 수 있어.

이런 공격을 방지하기 위해 파일 업로드 기능에 여러 가지 보안 대책을 적용해야 해.

### 2) 보기별로 이해하기

**① 업로드되어 저장되는 파일의 타입, 크기, 개수, 실행 권한을 제한해야 한다.**

이 내용은 올바른 대응 방안이야.

파일을 업로드할 때 아무 파일이나 무제한으로 허용하면 안 돼.

예를 들어 다음과 같이 제한할 수 있어.

- 파일 종류: JPG, PNG 등 허용된 형식만 업로드
- 파일 크기: 최대 10MB까지만 허용
- 파일 개수: 한 번에 업로드할 수 있는 파일 개수 제한
- 실행 권한: 업로드된 파일이 서버에서 실행되지 않도록 제한

특히 업로드된 파일에 실행 권한이 부여되면 악성 스크립트가 실행될 위험이 있으므로 주의해야 해.

**② 업로드되어 저장되는 파일은 외부에서 식별되지 않아야 한다.**

이 내용도 올바른 대응 방안이야.

업로드된 파일의 실제 저장 위치나 내부 파일명을 외부에서 쉽게 알아낼 수 없도록 관리하는 것이 좋아.

예를 들어 사용자가 다음 파일을 업로드했다고 해보자.

```text
myprofile.jpg
```

서버에 저장할 때는 원래 파일명을 그대로 사용하지 않고 무작위 파일명이나 별도의 식별자를 사용하는 방식이 있어.

```text
a8f92c1d7e.jpg
```

이렇게 하면 외부에서 파일명을 예측하거나 특정 파일에 직접 접근하기 어려워져.

다만 파일명을 숨기는 것만으로 파일 업로드 취약점이 완전히 해결되는 것은 아니야. 실제 접근 권한과 저장 위치도 안전하게 관리해야 해.

**③ 파일 업로드 기능이 필요 없다면 해당 기능을 삭제한다.**

이 내용도 올바른 대응 방안이야.

사용하지 않는 기능은 공격자가 악용할 수 있는 공격 지점이 될 수 있어.

예를 들어 웹사이트에서 파일 업로드 기능이 필요하지 않다면 해당 기능을 제거하는 것이 좋아.

불필요한 기능을 제거하면 공격에 노출될 수 있는 부분도 줄어들어.

**④ 파일명에 경로조작이 가능한 '..', '/', '\' 문자는 제거하고 사용할 수 있도록 필터링한다.**

이 보기가 정답이야.

여기서 조금 헷갈릴 수 있어.

`..`, `/`, `\`는 파일 경로를 조작할 때 악용될 수 있는 문자들이야.

예를 들어 다음과 같은 경로가 있다고 생각해 보자.

```text
/upload/profile.jpg
```

그런데 공격자가 파일명에 경로 이동을 의미하는 `../` 등을 포함시키면 원래 허용된 업로드 경로를 벗어나 다른 위치에 파일을 저장하도록 시도할 수 있어.

이런 공격을 디렉터리 경로 조작(Path Traversal)이라고 해.

그렇다면 왜 ④번이 틀렸을까?

문제의 핵심은 위험한 문자를 단순히 제거하는 블랙리스트 방식만으로 안전하다고 볼 수 없다는 점이야.

공격자는 인코딩이나 다양한 우회 방법을 이용해 필터링을 피할 수 있어.

따라서 단순히 특정 문자만 제거하는 방식에 의존하면 안 돼.

더 안전한 방법은 다음과 같아.

- 파일명에 허용된 문자와 형식만 사용하는 화이트리스트 검증
- 서버에서 파일명을 무작위로 새로 생성
- 경로를 정규화하고 실제 저장 경로가 허용된 디렉터리 내부인지 확인
- 사용자가 입력한 파일명을 경로에 직접 연결하지 않기

즉, 위험한 문자를 제거하는 것만으로 충분하다고 보는 것이 잘못된 거야.

### 3) 정답이 ④번인 이유

④번은 경로 조작 문자를 단순히 제거하는 방식만 제시하고 있어.

이러한 블랙리스트 방식은 우회될 가능성이 있기 때문에 안전한 파일 업로드 대책으로 충분하지 않아.

따라서 정답은 ④번이야.

### 4) 시험 암기

- 파일 종류 제한 = 화이트리스트 검증
- 파일 크기 제한 = 크기 제한
- 파일 개수 제한 = 개수 제한
- 실행 권한 제한 = 서버에서 파일 실행 방지
- 파일명 무작위 변경 = 파일명 예측 방지
- 경로 정규화 및 저장 위치 검증 = 경로 조작 방지

**핵심 암기:**
파일 업로드 취약점에서 특정 위험 문자만 제거하는 블랙리스트 방식에 의존하면 안 돼.

## 7. 다음 내용의 FTP 보안 대책으로 옳은 것은?

**정답: ② 익명 FTP 보안 대책 수립**

### 1) 문제 이해하기

문제에서 제시한 내용은 다음과 같아.

"불가피하게 익명 접속을 허용해야 할 때도 익명 업로드(쓰기 기능)는 절대로 허용하지 않는다."

여기서 핵심 단어는 익명 접속과 익명 업로드야.

먼저 FTP가 무엇인지부터 알아보자.

### 2) FTP란?

FTP(File Transfer Protocol)는 네트워크를 통해 파일을 전송하기 위한 프로토콜이야.

쉽게 말하면 컴퓨터와 서버 사이에서 파일을 주고받을 수 있도록 해주는 통신 규칙이야.

예를 들어 다음과 같은 작업에 사용할 수 있어.

- 서버에 파일 업로드
- 서버에서 파일 다운로드
- 서버의 파일 목록 확인
- 파일 및 디렉터리 관리

### 3) 익명 FTP란?

일반적인 FTP 서버에 접속하려면 사용자 이름과 비밀번호가 필요해.

그런데 익명 FTP(Anonymous FTP)는 별도의 개인 계정 없이도 서버에 접속할 수 있도록 허용하는 방식이야.

보통 다음과 같은 계정 이름을 사용해.

```text
anonymous
```

익명 FTP를 허용하면 사용자 인증 없이도 파일을 다운로드할 수 있기 때문에 공개 자료를 배포하는 용도로 사용할 수 있어.

하지만 보안상 위험도 존재해.

### 4) 익명 업로드를 허용하면 왜 위험할까?

익명 접속을 허용하면서 파일 업로드까지 허용한다고 생각해 보자.

그러면 공격자가 별도의 인증 없이 FTP 서버에 파일을 업로드할 수 있어.

예를 들어 다음과 같은 문제가 발생할 수 있지.

- 악성 파일 업로드
- 불법 파일 저장 및 배포
- 서버 저장 공간 고갈
- 서버 내부에서 사용되는 파일을 악성 파일로 교체하려는 시도

그래서 익명 FTP를 불가피하게 허용해야 한다면 일반적으로 다운로드만 허용하고 업로드나 쓰기 권한은 허용하지 않아야 해.

즉, 익명 사용자는 파일을 읽을 수는 있지만 서버에 파일을 작성하거나 수정할 수 없도록 제한하는 거야.

### 5) 정답이 ②번인 이유

문제에서 익명 접속을 허용하더라도 익명 업로드는 절대로 허용하지 않는다고 설명하고 있어.

이것은 익명 FTP를 사용할 때 적용해야 하는 보안 대책이야.

따라서 정답은 ② 익명 FTP 보안 대책 수립이야.

### 6) 다른 보기가 틀린 이유

**① FTP 서비스는 디폴트로 서비스 중지 상태 유지**

- FTP 서비스를 사용하지 않는다면 서비스를 중지하는 것이 보안상 좋아.
- 불필요한 서비스를 중지하면 공격자가 접근할 수 있는 경로를 줄일 수 있어.
- 하지만 문제에서는 FTP 서비스를 사용한다는 전제하에 익명 접속과 업로드 권한에 대한 대책을 설명하고 있어.

**② 익명 FTP 보안 대책 수립**

- 익명 FTP 접속을 불가피하게 허용해야 할 때 적용하는 보안 대책이야.
- 익명 사용자의 업로드 및 쓰기 권한을 제한해야 해.
- 정답이야.

**③ 최신 FTP 애플리케이션 유지**

- FTP 서버 프로그램을 최신 버전으로 유지하는 보안 대책이야.
- 알려진 취약점이 악용되지 않도록 보안 업데이트를 적용하는 것이지.
- 익명 업로드를 금지하는 내용과는 직접적인 관계가 없어.

**④ TFTP 보안 대책**

- TFTP(Trivial File Transfer Protocol)는 간단한 파일 전송 프로토콜이야.
- 일반 FTP와 달리 사용자 인증이나 디렉터리 목록 기능 등이 없는 단순한 방식이야.
- 문제에서 설명하는 익명 FTP의 업로드 제한과는 다른 내용이야.

### 7) 시험 암기

- FTP = 파일 전송 프로토콜
- Anonymous FTP = 익명 FTP
- 익명 FTP를 허용해야 한다면 다운로드 위주로 제한
- 익명 업로드 및 쓰기 권한 금지
- 사용하지 않는 FTP 서비스는 중지

**핵심 암기:**
익명 FTP를 허용하더라도 익명 업로드는 금지한다.

# 시험 직전 핵심 암기 노트

## 1. 이메일 시스템

- SMTP: 메일 전송 프로토콜
- MTA: 메일 서버 간 전달
- MUA: 사용자가 사용하는 메일 프로그램
- MDA: 사용자의 메일함에 메일 저장

## 2. 예외처리

- HTTP 500 = Internal Server Error
- 오류 발생 시 별도의 오류 페이지 표시
- 상세한 서버 내부 오류 정보 노출 방지
- 관련 설계 항목 = 예외처리

## 3. Command Injection

- Runtime.getRuntime().exec() = 운영체제 명령어 실행
- 사용자 입력값을 명령어에 그대로 연결하면 위험
- 악의적인 명령어가 실행될 수 있음
- 대응 방법 = 입력값 검증 및 안전한 명령어 실행

## 4. SQL Injection

- Blind based = 참/거짓 응답으로 정보 추측
- Error based = 오류 메시지로 정보 획득
- Union based = UNION으로 조회 결과 결합
- Stored Procedure based = 저장 프로시저 악용

## 5. DNSSEC

- NSEC = 존재하지 않는 DNS 데이터 증명
- RRSIG = 전자서명
- DNSKEY = 공개키
- DS = 상위 영역과 하위 영역의 신뢰 관계 연결

## 6. 파일 업로드 취약점

- 파일 타입 제한
- 파일 크기 및 개수 제한
- 실행 권한 제한
- 서버에서 파일명 변경
- 경로 정규화 및 저장 위치 검증
- 단순한 블랙리스트 필터링에만 의존하지 않기

## 7. FTP 보안

- FTP = 파일 전송 프로토콜
- Anonymous FTP = 익명 FTP
- 익명 접속을 허용하더라도 업로드 및 쓰기 권한은 금지
- 사용하지 않는 FTP 서비스는 중지

# 이번 문제에서 특히 기억해야 할 것

1. MTA와 MDA를 헷갈리지 말 것.
   - MTA는 다른 메일 서버로 전달
   - MDA는 사용자의 메일함에 저장

2. HTTP 500 오류 페이지 설정은 예외처리와 관련이 있음.

3. Runtime.getRuntime().exec()에 사용자 입력값이 들어가면 Command Injection을 의심할 것.

4. 참과 거짓에 따른 응답으로 데이터베이스 정보를 추측하면 Blind SQL Injection.

5. NSEC는 데이터가 존재한다는 증명이 아니라 존재하지 않는다는 사실을 증명함.

6. 파일 업로드 취약점은 특정 위험 문자만 제거하는 블랙리스트 방식에 의존하면 안 됨.

7. 익명 FTP를 허용하더라도 익명 업로드는 금지해야 함.
